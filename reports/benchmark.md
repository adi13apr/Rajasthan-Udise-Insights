# Performance benchmark

Generated by `scripts/benchmark.py` on 2026-10-20. Real timings from one machine;
they will differ on other hardware.

**Query:** KOTA enrolment by grade and gender, 2025-26. Every approach returned the same 27 rows (456,300 students), checked by the script.

**Machine:** 12th Gen Intel(R) Core(TM) i5-1240P, 16 logical cores, 15.7 GB RAM, Windows-11-10.0.26100-SP0; Python 3.13.0, DuckDB 1.5.6 (16 threads).

**Method:** cold = new DuckDB connection for each of 5 runs (DuckDB caches empty; the operating system's file cache was not cleared). Warm = 10 runs in one connection after one untimed run. Medians, with the fastest run in brackets.

| Approach | Data it reads | Cold median (ms) | Warm median (ms) | Cold vs raw CSV |
|---|---|---:|---:|---:|
| 1. raw CSV (read_csv_auto) | 67.9 MB of CSV (2025-26 profile + enrolment) | 885.4 (852.9) | 875.1 (845.3) | 1.0x |
| 2. bronze Parquet, no partition pruning | 21.9 MB of Parquet (both years) | 136.6 (134.1) | 187.2 (151.8) | 6.5x |
| 3. bronze Parquet, partition pruning (year=) | 11.2 MB of Parquet in the 2025-26 partition | 199.3 (176.6) | 222.1 (201.7) | 4.4x |
| 4. gold star schema | 33.8 MB DuckDB file (all gold tables) | 26.7 (19.5) | 15.1 (12.1) | 33.2x |

## What makes the difference

- **Column pruning (Parquet, DuckDB tables).** Columnar storage lets a query read only the columns it uses. A CSV has to be read and split line by line, every column.
- **Types decided once.** `read_csv_auto` guesses column types on every read; bronze stores text (typed in the query), silver and gold store real integer types.
- **Partition pruning.** Bronze is stored as `year=<YYYY-YY>/` folders, so a filter on the partition column lets DuckDB skip the other year's data. Its effect at this data size is measured separately below.
- **Modelling.** Gold has already done the work: the unpivot to one row per grade and gender, typing, de-duplication (the Kota test copies), and the school's district for each year (SCD2). The query is a join of a narrow fact table to small dimensions.

## Partition pruning, isolated

Counting the 2025-26 rows of bronze enrolment, four ways (25 cold runs each; the middle half of the runs fell between p25 and p75):

| How the files are read | Rows | Cold median (ms) | p25-p75 (ms) |
|---|---:|---:|---:|
| only the year=2025-26 folder (path points at the partition) | 533,892 | 13.7 | 12.6-15.3 |
| all files, filter on the _year column inside the files | 533,892 | 22.1 | 19.7-23.4 |
| all files, partition filter year = (no union_by_name: loses columns) | 533,892 | 13.5 | 9.9-15.0 |
| all files, partition filter year = + union_by_name | 533,892 | 17.3 | 15.1-20.0 |

All four scans take 13.5-22.1 ms, and their order changes from one run of this script to the next. In this run the full query with the partition filter (approach 3, 199.3 ms) was **not** faster than without it (approach 2, 136.6 ms). Conclusion: with about 11 MB per year, partition pruning makes no meaningful difference here; it pays off when partitions are large (many years, or many states). What does make a difference at this size is the storage format and the modelling (table above: up to 33x).

## A correctness trap found by this benchmark

The first version of approach 3 left out `union_by_name = true`. DuckDB then takes the column list from the first file it finds, a 2024-25 file, which has no transgender columns (they start in 2025-26). The query ran without error but silently returned one student fewer (Kota's only transgender student in classes 1-12). The script compares the answers of all approaches before reporting any timing, which is how this was caught. The pipeline always reads multi-year Parquet with `union_by_name = true`.

Raw CSVs were extracted from the zips into `data/tmp/` (gitignored) for approach 1; the zips in `data/raw/` were only read.
